## 2026-10-30 · 审批改为按发起方路由（issue #89）

**为什么改**
#78 定的是「两个渠道同时弹、先点先算」。实际用下来三个问题：两边同时打扰；
结果归属不可预期，排查困难；为了竞速必须先抢监听优先级，链路耦合。

**改了什么**
谁的会话发起，就只在那个渠道审批：企微会话的请求由企微独占（不调用下游），
其余请求直接交回网页端。注册仍然带 `prepend`——不带就抢不到发言权（见 #85）。

**当时的选项**
- 双渠道竞速 / 按会话归属路由 / 按「这一轮是谁发起的」路由 → 选按会话归属
- 保留 `broadcast` 开关 / 只做单一模式 → 选只做单一模式（少一个分支少一处不确定）

**为什么这么选**
路由比竞速简单：竞速要处理「另一边后到的回复怎么作废」，路由根本不存在这个问题。
用户也明确要「谁发的谁谈」，不需要两种模式并存。

**怎么验证**
`pnpm test` 44 条全绿、`tsc` 通过、`build:host` 后 `node --check` 通过。
真机：企微会话触发提权只出企微卡片；网页会话触发提权只出网页弹窗。

**留下的限制**
同一个企微会话在网页里继续对话时，审批仍会发到企微——因为归属按会话算，不按某一轮算。

## 2026-10-30 · 修复：审批监听挂错上下文（issue #81）

**为什么改**
#78 上线后真机验证失败：触发提权时**只有浏览器弹框，企微收不到卡片**。
代码在跑、测试全绿，但功能完全没生效。

**改了什么**
把审批应答方从插件根上下文挪到每个 Agent 自己的上下文（`installApprovalRelay(agentCtx, st)`），
并在 Agent 上下文卸载时注销。

**当时的选项**
- 注册在插件根（#78 的做法） / 注册在 Agent 上下文 → 只能选后者
- 在 `installWecomChannel` 里注册 / 在 `attach()` 里用 `agent.ctx` 注册 → 选后者：
  create 路径的 setup 上下文不一定是 Agent 自己的上下文

**为什么这么选**
审批事件按 Agent 作用域分发（`scopeTarget(agent, agent)`），只有挂在该 Agent 上下文链上的监听能收到。
注册在插件根上不会报错、不会警告，**静默地永远收不到**——这是本次最贵的教训。

**怎么验证**
`pnpm test` 44 条全绿；`pnpm run build` 后 `node --check lib/index.js` 通过；
真机：提权触发后企微与浏览器同时收到审批，谁先点谁生效。

**留下的限制**
作用域问题没有编译期保护，只能靠真机验证；单测覆盖不到，属于「必须手测」的改动。

## 2026-10-30 · 审批转接（issue #78）

**为什么改**
企业微信通道没有任何审批应答方。工具被沙盒拒绝后，DSH 发起的审批请求没有接收人，
按「拿不到答复就拒绝」直接失败；插件此前只注入一句「本通道没有确认框，禁止调用提问工具」，
属于绕开而不是解决。

实测触发点（同日排查）：受限沙盒会拦截进程访问系统钥匙串，`gh auth status` 因此报
「令牌无效」，而完整权限下同一条命令正常——报错文案把方向带偏成「令牌过期」。
要跨过这类权限边界，需要「命令被拒绝 → 提权重试 → 用户批准一次」这条链路可用。

**改了什么**
新增审批转接：审批请求转成企微按钮卡片，点按后放行一次；卡片失败降级纯文本。
细节见说明文档「审批转接」一节。

**当时的选项**

| 决策点 | 选项 | 选定 |
|---|---|---|
| 范围 | 只做审批 / 连提问工具一起做 | 只做审批 |
| 交互 | 卡片 / 纯文本 / 卡片为主 + 文本兜底 | 卡片为主 + 文本兜底 |
| 谁能批 | 白名单任何人 / 只认发起者 / 群内任何人 | 只认发起者 |
| 超时 | 不设 / 固定 / 可配置 | 可配置，默认 5 分钟 |
| 与网页端并存 | 先到先得 / 企微优先 / 禁用网页端 | 先到先得 |
| 参数展示 | 只显示工具名 / 关键参数摘要 + 脱敏 / 全量 | 摘要 + 脱敏 |
| 多待批 | 串行 / 全部并发 / 只发最新 | 串行，提示剩余数量 |
| 群聊 | 不启用 / 启用但只认发起者 / 任何人可批 | 启用，只认发起者 |
| 默认开关 | 默认开 / 默认关 / 按工作区 | 默认开 + 总开关 |
| 超时后告知 | 静默 / 主动告知 | 主动告知 |
| 同类自动放行 | 做 / 不做 | 不做 |
| 发送目标 | 按发起窗口反查 / 最近活跃 / 固定目标 | 反查，查不到即拒绝 |
| 断线 | 立即拒绝 / 等 30 秒 / 等满超时 | 等 30 秒 |
| 卡片失败 | 重试后降级文本 / 直接文本 / 直接拒绝 | 重试后降级 |
| 审计 | 只靠 DSH 记录 / 另存轻量记录 | 另存（按月切分，不含参数） |

**为什么这么选**
审批等于一次性提权。每个放行口子都要能回答三个问题：谁替谁放行、多久失效、出事后能不能查到人。
所以：只认发起者（别人不能替我放行）、只放行一次（不造长期口子）、记录留痕（能追到人）。

**怎么验证**
`pnpm test` 全绿（新增 14 条用例覆盖脱敏、文本解析、按钮 key、卡片渲染、队列串行/排队结算/
发送失败/清空）；`pnpm run build:host` 后 `node --check lib/index.js` 通过。
真机验收（需人工）：越界写文件收到卡片 → 点同意放行一次；再次触发重新询问；
群里非发起者点按被拒；5 分钟不操作超时拒绝。

**留下的限制**
卡片被点后企微要求 5 秒内回执才能更新卡片，网络差时卡片停留在「待审批」样子，
结果以随后文字回执为准；审批记录只存身份与时间，不存命令参数。

## 明确不做的事

| 决定 | 理由 | 日期 |
|---|---|---|
| 不做「同类操作自动放行」 | 与「只放行这一次」的语义冲突，等于自造长期放行口子 | 2026-10-30 |
| 群聊不做「任何人可批」 | 审批是「我让你做这件事」的延续，别人不该替我放行 | 2026-10-30 |
| 不在本次接 `ask_user_question` | 提问工具是另一套阻塞机制，一个改动只解决一个机制 | 2026-10-30 |
