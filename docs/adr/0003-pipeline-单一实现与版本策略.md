# ADR-0003：pipeline 做成单一实现包，各仓钉稳定文件名

**状态**：已接受（2026-11-01）
**影响范围**：`self-dsh-plugins`、`agent-mobile`、`homebase`，以及后续接入的 `memx` / `llm-wiki` / `wrongmathf4`

## 背景

交付流程（issue → worktree → PR → 审核 → 合并）在本机已经跑了五个仓，但实现是**每仓一份**：
`agent-mobile` 与 `homebase` 各自有一份 `merge-pr.sh`（无审核闸门），`self-dsh-plugins` 有一份带闸门的，
其余仓连 pipeline 都没有。结果是「规则改了，别的仓跟不上」——2026-11-01 引入审核闸门时，
只有本仓有闸门，其他仓合并时零校验。

同时，安全件（闸门判定、审核记录、高风险清单）分散在多份脚本里，任何一份写得不一样，
就会出现「这个仓能合、那个仓不能合」的静默不一致。

## 决策

### 1. 一个独立仓，一个包

新建 `~/workspace/dsh-pipeline`，包名 `@guraul/dsh-pipeline`，**不发布到任何 registry**。
它是所有仓的交付流程与审核流程的单一实现。

否决：
- **逐仓复制**：五份闸门，改一处要改五处；
- **git submodule**：与本仓的 worktree 习惯冲突（`.worktrees/` 里 submodule 状态要重建）；
- **全局 bin（`~/.dsh/bin`）**：版本随改随变，且 GitHub Actions 上没有这个 bin。

### 2. 包的范围包括审核方

包不只装「交付流程」，也装**审核编排**（准备材料、调用 reviewer、发布结论）。
`dsh-subagents` 退化为「DSH 会话里的入口」：只保留 `product_delegate` / `product_continue`
两个工具与角色加载——因为工具注册依赖宿主 API，不能让通用包反向依赖 DSH 版本。

### 3. 唯一的执行出口是封装后的 `gh` / `git`

包内的 `lib/gh.mjs`、`lib/git.mjs` 只暴露固定签名的操作（`mergePr`、`createWorktree`、`commentPr`…），
调用方拿不到「拼任意 argv」的能力。业务命令（如 `pnpm test`）走配置白名单，越界由审计脚本报出。

否决：**只靠白名单**——那是运行期检查参数，总能被 `spawn('gh', ...)` 绕过；API 层没有那个入口。

### 4. 版本：稳定文件名 + 编号 tarball

各仓依赖的是**固定文件名** `dsh-pipeline-latest.tgz`，内容可以前进；同时每次发布保留
`dsh-pipeline-<版本>.tgz`，回滚时把 `package.json` 指回编号文件即可。

这条是**非直觉选择**，必须写明理由：本机没有 registry，`file:../dsh-pipeline` 永远吃最新、
钉不住版本；而用户要求「各仓不用逐个升版本」。用稳定文件名换「升级零操作」，
用编号 tarball 保留回滚能力，是这个组合里唯一能同时满足两者的做法。

护栏：**包自己的门禁（单测 + 契约测试）通过，才替换 `latest.tgz`**。统一最新的代价由这道门禁承担。

产物落在 `dsh-pipeline/dist/`，**不入库**（`.gitignore` 忽略全部 `*.tgz`）；`latest.tgz` 与编号 tarball 都在本机保留。

否决：
- **git tag 依赖**（`git+file://…#v1.2.0`）：依赖 pnpm 对 `git+file` 的支持细节，CI 上还要能 clone；
- **各仓 `vendor/` 内置产物**：等于把单一实现又复制成五份。

### 5. 闸门只在本地运行

所有仓都在本机，合并动作也由本机的 executor 发起；GitHub Actions 只做构建与部署，**不消费
`dsh-pipeline`**。因此闸门不需要在 CI 上可用，`dist/*.tgz` 也不入库——仓库里只有源码。

代价写清楚：换机器或换人时，必须先在 `dsh-pipeline` 里 `pnpm pack` 出产物，否则消费仓的
`file:` 依赖装不上。这条代价可接受，因为「本机」是这个工作流的既定前提。

否决：**把 tarball 提交进库**——用二进制换「零配置」不值得，且会让每次发版都多一个无法 review 的文件。

### 6. 默认值叠加，覆盖必须显式

角色（executor / reviewer / 未来的角色）与高风险清单：**包给默认，仓可覆盖或追加**，
覆盖写在 `.dsh/pipeline.json` 里、可审计。新增角色以改代码为主（配置只调参数）。

### 7. 记录增三个字段

`schemaVersion`（结构）、`policyVersion`（闸门规则版本，取包版本号）、`round`（第几轮）。
三者失效方式不同：结构决定「能不能读」，规则版本决定「当时按什么判」，轮次决定「是不是超限」。

### 8. 迁移顺序：本仓先行

1. 建包 → 2. **本仓切换并跑通一轮完整循环**（含 REJECT→修复→复审）→ 3. 回去做 reviewer 插件的后续
→ 4. 全部做完再推其他仓（按需，不设截止）。

理由：本仓是唯一同时在跑审核循环的仓，先切它才能用真实循环验证包；但也不能一次推五个仓，
因为没有第二套可用流程兜底。

### 9. 共存与回滚

切换期间旧 `scripts/pipeline/*.sh` 改为**转发 + 警告**，该仓合并两次成功后删除。
回滚只靠「改 `package.json` + 重装」，不提供 `rollback` 子命令——回滚必须是最不可能出错的动件。

### 10. 等价验收

- 包内单测：`gate` / `record` / `policy` 的纯函数；
- 契约测试：桩环境里跑每个消费仓的「开 PR / 合并」全流程，断言命令序列；
- **字段级 diff**：同一份请求文件，新旧实现产出的记录除 `policyVersion` 外逐字段相同。

## 后果

- 好处：闸门与记录只有一份实现，规则变更一处生效；高风险清单可按仓扩展。
- 代价：包成为所有仓的**单点故障**——包坏了五个仓都合不了；因此包自身的门禁必须比任何消费仓都严。
- 代价：产物不入库，**换机器/换人要先 `pnpm pack`**；这是「只在本地跑」的直接结果。
- 风险：`latest.tgz` 内容前进是**不可见的变更**（文件名没变）。缓解：包每次发布都要在 PR 里
  写清「本次变更影响哪些仓的哪种行为」，并保留编号 tarball。

## 未决

- 包内模块划分与文件清单：见二期首个 issue；
- `policyVersion` 的递增规则（每次发版都变，还是仅规则变更时变）：待实现时定。
