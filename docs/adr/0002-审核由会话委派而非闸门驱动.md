# 审核由会话委派，而不是由闸门驱动

**状态**：accepted（2026-11-01），取代 PR1 方案里「CLI 发起审核 + 闸门驱动流程」的设计

最初的方案把 `merge-pr.sh` 的审核闸门当作流程中心：脚本组装请求、调 reviewer、写记录、自己判定能不能合。讨论后确认这条路走不通——**闸门只能回答「能不能合」，回答不了「该谁去改、改完给谁看」**。于是把中心换成控制面会话：它委派 `executor` 开 PR、委派 `reviewer` 审、reviewer 写 PR comment 并提交 review 状态，再由 reviewer 委派 `executor` 修复或合并；闸门退化成合并那一刻的最后一道校验。轮次（3 轮）由控制面计数，人只在 `ESCALATE`、高风险路径、轮次超限时被叫。

## 考虑过的选项

- **闸门驱动**：脚本是唯一入口，不依赖会话。被否决——它无法表达「谁去改」，也无法表达「再审一次」，而这些正是流程的主要内容。
- **CLI 发起形态 A**（`review --form a` 经本地 HTTP）：被否决——CLI 进程没有会话、没有父 agent，DSH 的 child agent 起不来；用 `ctx.llm` 做一次性补全能跑，但没有工具、读不了仓库，挂同一个名字等于骗人。
- **用 label 表达审核状态**：被否决——机器账号到位后，GitHub 原生 review 状态（`APPROVED` / `CHANGES_REQUESTED`）就是标准答案，label 属于重复表达。

## 后果

- `merge-pr.sh` 的定位改变：从驱动者变成防线。它的 fail-closed 行为不变。
- reviewer 的权限扩大：从「只读、不写 PR」变成「不改代码，但写 comment、提交 review 状态、写审核记录、委派 executor」。这与 REQ-001 §5 的原始表述冲突，已在设计文档的偏差清单里登记。
- 必须有两个 GitHub 身份：PR 由主账号开，review 由机器账号提交——GitHub 不允许同一账号 approve 自己的 PR。
- 形态 A 只能由会话内 agent 发起；这一点写进 CLI 的拒绝路径，而不是留一个假的实现。
