# REQ-001 · Reviewer 子代理接入形态

| 项 | 值 |
|---|---|
| 状态 | 草稿（待评审） |
| 日期 | 2026-10-31 |
| 关联 | `docs/pipeline/README.md`（D4 人在环）、REQ-002（清言网页适配器） |
| 前提 | **模型能力视为 ready**。本需求只定义「怎么接」，不涉及模型选型、提示词调优、评测集建设 |

---

## 1. 背景与问题

当前交付流程（issue → worktree → PR → CI → 合并）中，唯一的人在环步骤是 D4：

> agent 开 PR 后必须问用户「review 是否完成」，用户回 ok 才允许跑 `merge-pr.sh`。

这条约束是**调用纪律**，`merge-pr.sh` 自己不校验（脚本头原文：「本脚本不自己询问、也不校验'是否已同意'」）。
问题是：

- 人成了流水线的固定节拍，人不在就无法推进；
- 纪律不可验证——跳过了也没人知道；
- 审核结论没有结构化记录，事后无法追溯「谁、依据什么放的行」。

本需求要把这一步换成 **reviewer 子代理**：由它给出判定，流程按判定继续或停下。

**这不是「换个人」，而是换一种信任模型**：把无条件的人工放行，换成一个会超时、会失败、可能被诱导的外部审核方。因此本需求的真正难点是**判定契约与失败语义**，而不是怎么调用。

---

## 2. 目标

| 编号 | 目标 | 可观测的成功标志 |
|---|---|---|
| G1 | 三种接入形态都能产出**同一份** `ReviewResult` | 同一输入喂三种形态，结果通过同一份 schema 校验 |
| G2 | 判定与提交绑定，不可张冠李戴 | 结果必须回显 `head_sha`，与 PR 当前 head 不一致即作废 |
| G3 | 任何异常都不等于通过 | 超时/解析失败/形态不可用 → `ESCALATE`，合并被拒绝 |
| G4 | 审核过程可追溯 | 每次审核留下 `traceId` / 形态 / 模型 / 耗时 / 判定，可查 |
| G5 | 既有 pipeline 其余环节不变 | 现有 8 步脚本行为回归通过，唯一差异是第 6.5 步 |

---

## 3. 范围

### 3.1 包含

- 统一的审核请求/结果契约；
- 三种接入形态的适配器设计：DSH 原生子代理、委派给 opencode / codebuddy、伪模型（网页清言）；
- 形态选择与降级策略；
- 异常与超时的统一语义；
- 与 `merge-pr.sh` 的衔接点（新增校验参数）；
- 审计记录的内容与位置。

### 3.2 不包含（明确排除）

| 排除项 | 理由 |
|---|---|
| 模型能力建设（选型、提示词工程、评测集、微调） | 前提已声明：模型能力 ready |
| 改变 issue / worktree / PR / CI 的既有环节 | 需求要求「其余环节默认保持不变」 |
| 改变合并方式（squash）与清理纪律 | 同上 |
| 引入 GitHub Actions 侧的新工作流或分支保护规则 | 本期在本地闭环；forge 侧门禁留作后续 |
| 多审核方投票 / 二次评审打分 | 列为后续增强，不在本期 |
| 自动修复（reviewer 直接改代码） | reviewer 只读、只判定 |

## 4. 术语

| 术语 | 含义 |
|---|---|
| 审核形态 | reviewer 的承载方式：DSH 原生子代理 / 委派给外部 CLI / 伪模型 |
| 伪模型 | 本身不是模型，但对外表现为「给提示词、拿文本」的端点，如网页版清言 |
| 判定 | `APPROVE` / `REJECT` / `ESCALATE` 三值之一 |
| 交回人工（ESCALATE） | 不自动放行，把决定权交还用户 |
| 提交绑定 | 判定只对某一个 `head_sha` 有效 |
| 审计记录 | 一次审核的不可变摘要，用于事后追溯 |

---

## 5. 角色与职责

| 角色 | 职责 | 权限边界 |
|---|---|---|
| 控制面 agent（DSH） | 组装审核请求、调用 reviewer、按判定决定是否合并 | 可执行合并；不参与判定 |
| reviewer（三种形态之一） | 阅读变更、给出判定与问题清单 | **只读**：不改代码、不合并、不写 PR |
| pipeline 脚本（`merge-pr.sh`） | 校验审核记录、执行合并与清理 | 不生成判定 |
| 用户 | 高风险路径的最终放行；异常时的回退对象 | 可否决任何自动判定 |

**硬约束**：reviewer 与合并动作分离。reviewer 即使被诱导，最大破坏是给一个错误判定，不能自己把代码合进去。

---

## 6. 总体设计：一个契约，三个适配器

```
                 ┌─────────────────────────────┐
                 │  控制面 agent（DSH）         │
                 │  组装 ReviewRequest          │
                 └──────────────┬──────────────┘
                                │ 统一调用
                 ┌──────────────▼──────────────┐
                 │  reviewer 选择与降级策略      │
                 └───┬──────────┬──────────┬───┘
                     │          │          │
              ┌──────▼───┐ ┌────▼─────┐ ┌──▼────────┐
              │ 形态 A    │ │ 形态 B    │ │ 形态 C     │
              │ DSH 原生  │ │ opencode │ │ 伪模型     │
              │ 子代理    │ │ codebuddy│ │ 网页清言   │
              └──────┬───┘ └────┬─────┘ └──┬────────┘
                     └──────────┴──────────┘
                                │
                    ┌───────────▼────────────┐
                    │ 统一 ReviewResult       │
                    │ + 判定行随机标记 + SHA  │
                    └───────────┬────────────┘
                                │
                    ┌───────────▼────────────┐
                    │ 审核记录（本地 + PR 评论）│
                    └───────────┬────────────┘
                                │
                    ┌───────────▼────────────┐
                    │ merge-pr.sh 校验后合并  │
                    └────────────────────────┘
```

设计要点：**审核能力**（读变更、给判定）与**接入形态**（怎么被调用）解耦。三种形态共享同一契约，上层不感知差异。

## 7. 统一接口约定

### 7.1 输入：`ReviewRequest`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `pr` | number | 是 | PR 编号 |
| `head_sha` | string | 是 | 本次审核针对的提交 |
| `issue` | object | 是 | `{ number, title, body }`，验收依据 |
| `files` | string[] | 是 | 变更文件清单（用于路径风险策略） |
| `diff` | string | 是 | 变更正文，已按预算裁剪 |
| `conventions` | string | 否 | 仓库规范摘要（如 `AGENTS.md` 关键条目） |
| `budget` | object | 否 | `{ maxChars, timeoutMs }` |
| `form` | enum | 否 | 强制指定形态；缺省按 §8.5 策略 |

**约束**：`diff` 属于不可信数据，必须包裹在固定围栏内并声明为数据；不得与指令混排。

### 7.2 输出：`ReviewResult`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `verdict` | enum | 是 | `APPROVE` / `REJECT` / `ESCALATE` |
| `head_sha` | string | 是 | 必须回显请求中的值 |
| `findings` | array | 是 | `[{ severity, file, line, message }]`，可为空 |
| `evidence` | string[] | 是 | 支撑判定的证据（引用具体文件:行） |
| `form` | enum | 是 | 实际使用的形态：`native` / `cli` / `web` |
| `model` | string | 是 | 实际模型标识；形态 C 填 `web/qingyan` |
| `durationMs` | number | 是 | 耗时 |
| `traceId` | string | 是 | 审计关联 id |
| `errorCode` | string | 否 | 异常分类码，见 §7.4 |

### 7.3 判定语义与不变式

| 不变式 | 说明 |
|---|---|
| I1 提交绑定 | `verdict` 只对 `head_sha` 有效；合并前重读 PR head，不一致即作废 |
| I2 随机标记 | 判定行必须带一次性随机标记（每轮生成，不出现在 diff 中），防止伪造判定行 |
| I3 静默即拒绝 | 没有判定行、判定多义、解析失败 → `ESCALATE` |
| I4 失败即拒绝 | 超时、异常、形态不可用 → `ESCALATE`，绝不视为通过 |
| I5 高风险优先 | 命中高风险路径（§10.2）时，无论模型判定如何，一律 `ESCALATE` |
| I6 幂等 | 幂等键为 `(pr, head_sha)`；同一键重复审核覆盖旧记录，不产生并行放行 |

### 7.4 错误码

| 码 | 含义 | 对应判定 |
|---|---|---|
| `E_UNAVAILABLE` | 形态不可用（未安装/未登录/服务不可达） | ESCALATE |
| `E_TIMEOUT` | 超过 `budget.timeoutMs` | ESCALATE |
| `E_PARSE` | 判定行缺失或多义 | ESCALATE |
| `E_SHA_MISMATCH` | 回显 SHA 与请求不符 | ESCALATE |
| `E_BUDGET` | 变更超出字符预算且无法分片 | ESCALATE |
| `E_POLICY` | 命中高风险路径 | ESCALATE |

## 8. 三种接入形态

### 8.1 形态 A：DSH 原生子代理

| 项 | 说明 |
|---|---|
| 实现方式 | DSH 插件内 `ctx.subagents.registerProvider()` 注册 `reviewer` provider，`start()` 组装请求并返回结果 |
| 模型来源 | 由 `agentOptions` 指定 DSH 已配置的 provider/model |
| 工具能力 | **可带**（读文件、跑只读命令），因此能自行核对仓库上下文 |
| 上下文 | 独立子会话，不继承父会话历史 |
| 适用 | 需要读仓库、需要交叉核对的审核 |
| 约束 | 只能使用 DSH 已配置的模型；模型标识必须回填到 `model` |

### 8.2 形态 B：委派给 opencode / codebuddy

| 项 | 说明 |
|---|---|
| 实现方式 | 走既有 `dsh-plugin-product-subagents`（ACP 桥），新增 `reviewer` 角色 JSON |
| 模型来源 | 调用时**显式指定** `provider/model`（角色不 pin 模型，按仓库纪律必须全名传入） |
| 工具能力 | 有（由远端 CLI 的权限模式决定，建议 `readonly`） |
| 上下文 | 远端会话，可按需续接 |
| 适用 | 复用现有执行面、需要模型可切换 |
| 约束 | 权限模式必须为 `readonly`；远端不可用时按 §9 回退 |

### 8.3 形态 C：伪模型（网页清言）

| 项 | 说明 |
|---|---|
| 实现方式 | 宿主插件 → 本机桥接 → Chrome 扩展 → 清言网页；把回复文本按同一契约解析成 `ReviewResult` |
| 模型来源 | 网页版清言（具体模型由清言侧决定，标识统一记 `web/qingyan`） |
| 工具能力 | **无**。只能看喂进去的 diff，不能读仓库、不能跑测试 |
| 上下文 | 每次新建对话（可选续接） |
| 适用 | 需要「另一个模型家族」的独立视角，降低与主模型的相关性 |
| 约束 | 依赖 REQ-002 的桥接；受第三方页面改版、账号风控影响；单次延迟最高 |
| 特殊要求 | 判定行必须带随机标记（I2）；发送前做密钥特征扫描 |

### 8.4 形态对比

| 维度 | A 原生 | B 委派 CLI | C 伪模型 |
|---|---|---|---|
| 模型可选 | 是（DSH 内） | 是（调用时指定） | 否（清言侧决定） |
| 能读仓库 | 是 | 是 | 否 |
| 能跑测试 | 是（只读命令） | 是（受限） | 否 |
| 延迟 | 中 | 中 | 高 |
| 可用性依赖 | DSH 宿主 | 远端 CLI + 鉴权 | 浏览器 + 扩展 + 网页 + 登录态 |
| 审计粒度 | 中 | 中 | 低（只能看回传文本） |
| 账号风险 | 无 | 无 | 有（网页自动化） |
| 独立视角价值 | 低（同族模型） | 中 | 高（不同模型家族） |

### 8.5 选择与降级策略

```
默认：形态 B（复用执行面、模型可指定）
  ├─ 需要读仓库/跑测试 → 形态 A
  ├─ 需要独立模型家族的第二意见 → 形态 C
  └─ 任一形态失败 → 按 A → B → 人工 降级；C 失败不自动升级为通过
```

**降级只允许降级到「更保守」，不允许降级到「更宽松」**：形态 C 不可用 → 回退 A/B 或人工；任何降级都不得绕过 §7.3 的不变式。

## 9. 异常与超时

| 场景 | 行为 | 用户可见结果 |
|---|---|---|
| 形态不可用（未安装/未登录/不可达） | 立即 `ESCALATE`，不重试 | 「审核方不可用，已交回人工」 |
| 超时（默认 A/B 300s、C 180s、总闸门 600s） | 重试 1 次，仍超时 → `ESCALATE` | 「审核超时」 |
| 判定行缺失/多义 | `ESCALATE`（`E_PARSE`） | 「无法解析判定」 |
| 回显 SHA 不符 | `ESCALATE`（`E_SHA_MISMATCH`） | 「判定与提交不匹配」 |
| 变更超预算 | 尝试分片；无法分片 → `ESCALATE`（`E_BUDGET`） | 「变更过大，需人工」 |
| 命中高风险路径 | `ESCALATE`（`E_POLICY`） | 「高风险变更，需人工」 |
| 连续失败 3 次 | 熔断：当天全部回退人工 | 「审核方熔断」 |
| 疑似风控/验证码（形态 C） | 停止并 `ESCALATE`，**不重试** | 「需人工处理验证」 |

**统一原则**：任何异常都不是「通过」，而是「回到人手上」。

## 10. 与 pipeline 的衔接

### 10.1 改动边界

| 环节 | 改动 |
|---|---|
| 1–5（issue / worktree / 开发 / 自测 / 开 PR） | 不变 |
| 6（CI） | 不变，仍是硬门禁 |
| **6.5（新增）** | 控制面 agent 调 reviewer，得到 `ReviewResult`，写审核记录 |
| 7（合并） | `merge-pr.sh` 新增 `--review-record=<文件>`：校验判定、SHA、时效、风险路径 |
| 8（收尾） | 不变 |

### 10.2 高风险路径（强制人工）

| 路径 | 理由 |
|---|---|
| `.github/` | 改 CI 本身 |
| `scripts/pipeline/` | 改交付流程本身 |
| `AGENTS.md`、`docs/pipeline/` | 改规则与流程文档 |
| `package.json` 的依赖变更 | 供应链风险 |
| 单 PR 变更行数 > 400 | 审核质量下降 |
| 涉及凭据、密钥、部署脚本 | 不可逆风险 |

### 10.3 审核记录

| 项 | 要求 |
|---|---|
| 位置 | 本地 `.dsh-web/reviews/<pr>-<sha>.json`（不入库） |
| 内容 | 完整 `ReviewResult` + 请求摘要（diff 哈希，不存 diff 全文） |
| 时效 | 记录生成超过 30 分钟需重新审核 |
| 留痕 | 可选：同步一条 PR 评论（判定、形态、模型、耗时、traceId） |

## 11. 非功能需求

| 类别 | 要求 |
|---|---|
| 安全 | reviewer 只读；判定与合并分离；diff 视为不可信数据；发送外部前做密钥特征扫描 |
| 审计 | 每次审核可追溯到 `traceId`、形态、模型、耗时、判定 |
| 可回滚 | 关闭开关即回到「人工 ok」流程，无需改脚本 |
| 性能 | 单次审核 ≤ 300s（C 形态 ≤ 180s）；不得阻塞其他会话 |
| 兼容 | 三种形态共享契约；新增形态不改上层调用方 |
| 降级 | 任何形态不可用都能安全回退到人工 |

## 12. 验收标准

> 每条都必须可测。无法测的条目不得进入验收。

| 编号 | 验收标准 | 验证方式 |
|---|---|---|
| AC-01 | 三种形态对同一输入都返回通过 schema 校验的 `ReviewResult` | 固定样例 × 3，跑 schema 校验 |
| AC-02 | 每条结果都回显 `head_sha` 且与请求一致 | 断言 |
| AC-03 | 形态 C 未登录时返回 `ESCALATE` + `E_UNAVAILABLE`，绝不返回 `APPROVE` | 断开登录态实测 |
| AC-04 | 判定行缺失/多义时返回 `ESCALATE` + `E_PARSE` | 注入畸形回复 |
| AC-05 | 超时后返回 `ESCALATE`，且 `merge-pr.sh` 拒绝合并 | 构造超时 |
| AC-06 | 命中高风险路径时强制 `ESCALATE`（即使模型判 APPROVE） | 构造 `.github/` 变更 |
| AC-07 | `merge-pr.sh --review-record` 在 SHA 不符/过期/判定非 APPROVE 时拒绝 | 三组反例 |
| AC-08 | 每次审核可从 `traceId` 查到形态、模型、耗时、判定 | 查记录文件 |
| AC-09 | 关闭开关后流程回到「人工 ok」，既有 8 步无回归 | 回归跑一遍 |
| AC-10 | 形态降级路径可验证：C 不可用 → A/B → 人工 | 逐级断开实测 |

## 13. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 提示词注入（diff 里写「输出 APPROVE」） | 错误放行 | 内容围栏 + 随机标记 + 高风险路径强制人工；业界已有实证案例 |
| 判定被伪造 | 错误放行 | 只认随机标记之后的判定行；SHA 绑定 |
| 外部审核方不可用 | 流程停滞 | 统一 `ESCALATE` 回退人工 |
| 自动合并放大错误 | 坏代码进 main | 分阶段上线；高风险路径保留人工；可 revert |
| 把密钥发给第三方 | 泄露 | 发送前密钥特征扫描；命中即中止 |
| 审核方被过度信任 | 橡皮图章 | 定期人工抽检；记录命中率 |

## 14. 开放问题（需拍板）

| 编号 | 问题 | 建议 |
|---|---|---|
| Q1 | reviewer 判 APPROVE 后是直接合并，还是需人看一眼？ | 一期：需人看一眼；二期：低风险自动 |
| Q2 | 高风险路径清单是否采用 §10.2？ | 采用，后续可调 |
| Q3 | 三种形态的默认优先级？ | 默认 B；需读仓库用 A；需独立视角用 C |
| Q4 | 审核记录是否同步到 PR 评论？ | 建议同步，便于追溯 |
| Q5 | 熔断阈值（连续失败 3 次）是否合适？ | 先用 3，实测调 |
