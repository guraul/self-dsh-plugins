## §6 已知陷阱与教训（每条都带解法）

1. **`list_subagent_models` 不是模型清单**。它只列「当前会话策略允许的子代理路由」。本会话里它只回 `opencode-go` 一个 provider，导致我误判「mimo 不存在」。解法：查模型看 `~/.dsh/profiles/web/cordis.patch.yml` 的 `llm-pi-ai.config.providers`；查策略看 `subagent-model-selection-settings`。
2. **子代理模型策略是会话级的**，只在会话创建时写入，旧会话永远不会补写。解法：验证模型必须开新会话；不要试图热重载或重启来「补」策略。
3. **本地产物版本号不具区分力**（三仓都写 `0.1.0`）。解法：用 `doctor` / `--version` 看构建标识；刷新 `tools/` 一律 `rm -rf node_modules pnpm-lock.yaml && pnpm install`，**不要用 `pnpm update`**。
4. **包 `merge` 的 `E_BRANCH_UNMERGED` 是 bug 不是现场问题**。解法：暂时手动 `git -C <main> branch -D -- <branch>`；根治见任务 2。
5. **判断「合并会不会触发部署」必须核对 `headSha`/`createdAt`**，不能只看 `gh run list` 有一条 success。各仓 `paths:` 不同：homebase 含 `scripts/**`（会部署），agent-mobile 只认 `agent-mobile-app/**`（不部署）。
6. **`review-loop.md` 说「reviewer 走形态 A」已过期**：现在 reviewer 走 B（`product_delegate` + codebuddy）。别按那句话去查 A 的代码。
7. **`new-task.sh` 的号必须来自 `gh issue create` 输出的最后一行**。本会话传错号两次，第二次撞进别的会话的 worktree。解法：先 `gh issue create` 拿到 URL，再从 URL 里取号。
8. **别在主工作区直接改码**。本会话犯过一次（改了 `dsh-subagents/lib/*.js`），发现后 `git checkout --` 还原再挪进 worktree。
9. **`merge --root` 要指主工作区**，指到 worktree 会导致「没有持有该分支的 worktree，跳过移除」，还得手动清理。
10. **`git worktree remove` 对主工作区会报 `fatal: … is a main working tree`**，清理必须用 `git worktree list --porcelain` 首条判断哪个是主工作区。
11. **PR 关掉后分支强推，GitHub 不允许 reopen**（`state cannot be changed … branch was force-pushed`）。解法：直接开新 PR，别纠结 reopen。

**代码红线**：只走 pipeline（issue → worktree → PR → 审核 → 合并）；禁止直推 main；squash 唯一；多行 body 用 `--body-file`；`gh api` 走 REST。

**上一棒的错（防重蹈）**：把旧 `gh run list` 的结果当成「这次合并的部署」并向用户索要了两次确认；把 `list_subagent_models` 的输出当成模型全集并断言「mimo 不存在」（用户当场用截图纠正）。
